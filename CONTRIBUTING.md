# Contributing to Hypercraft Repositories

This applies to every Hypercraft repository unless that repository has its own `CONTRIBUTING.md`. Repository rules may add requirements but may not weaken company standards.

**Hypercraft staff and contractors:** the authoritative standards live in the internal [engineering-standards](https://github.com/hypercraftusa/engineering-standards) repository. The links on this page need org access. This page is a quick guide. If it conflicts with that repository, the standards repository wins.

**External contributors:** open an issue to discuss a change before submitting a pull request. Don't include confidential or customer information in issues or PRs. A Hypercraft maintainer will handle the internal requirements below.

## Before you start

- **Link a work item.** Every change targeting `main` needs an issue or requirement. Typo and formatting fixes are exempt.
- **Classify the risk (L0–L3).** Base it on what happens if the software fails, not on how it was written. See [Risk Classification](https://github.com/hypercraftusa/engineering-standards/blob/main/standards/software/classification.md).
- **Plan nontrivial work first.** Write down the intended behavior, acceptance criteria and how you will verify it before writing substantial code. A short note in the issue is usually enough.

## While you work

- Keep PRs focused. Don't mix refactoring, dependency updates and behavior changes without a reason.
- Follow the [Development](https://github.com/hypercraftusa/engineering-standards/blob/main/standards/software/development.md) and [Testing](https://github.com/hypercraftusa/engineering-standards/blob/main/standards/software/testing.md) standards and the repository's own build and style docs.
- Never commit secrets, credentials or customer data.
- If you use AI tools, follow the [AI Development Guidelines](https://github.com/hypercraftusa/engineering-standards/blob/main/ai/development-guidelines.md) and the Hypercraft AI Use Policy. Use only approved tools and accounts for company code. You are responsible for AI-generated code, the same as code you write yourself.

## Opening a pull request to `main`

Fill in the PR template. It asks for:

1. What changed and why
2. The linked work item or requirement
3. The risk level (L0–L3)
4. What verification you ran, the results and any known limitations. Don't list tests you didn't run.
5. Whether AI made a material contribution. If it did, say which parts, what you decided or changed yourself, and how you checked the result.
6. Confirmation that you have read the whole diff and can explain it

Tests generated by the same AI that wrote the code are useful, but passing them alone doesn't show the code is correct. Check behavior against requirements or other evidence that doesn't come from that AI.

PRs to other branches may use lighter documentation unless the repository says otherwise.

## Review and merge

- `main` requires an independent human reviewer. You can't be your own only reviewer, and AI review doesn't count toward required approvals.
- L3 changes require the designated technical authority. See [Code Review](https://github.com/hypercraftusa/engineering-standards/blob/main/standards/software/code-review.md) and [Engineering Review and Approval](https://github.com/hypercraftusa/engineering-standards/blob/main/governance/engineering-review.md).
- **Merging is not releasing.** Deployment, release and operational adoption need their own approvals.

## Exceptions and questions

Exceptions must be approved by engineering leadership **before** you use them. Send questions about these standards, or proposed changes to them, to the `engineering-standards` repository.
